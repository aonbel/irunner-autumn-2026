# Дизайн харнесса irunner

Документ описывает архитектуру решения до начала реализации. Основан на
регламенте соревнования (`statement/Регламент соревнования.md`), примерах
задач (`statement/task-dir`) и уточнениях организаторов.

## 0. Уточнения организаторов (зафиксировано)

- openJiuwen использовать **обязательно**.
- Бюджет — **100 000** выходных токенов, передаётся в `BUDGET`
  (например, `BUDGET=100000`). При превышении LLM перестаёт отвечать.
- Информации об остатке бюджета прокси **не даёт** — считаем сами.
- За пропуск невыполнимой задачи баллов нет.
- Невыполнимая задача — та, которую **нельзя точно решить при имеющихся
  данных**.
- Для невыполнимой задачи **не создавать `answer.txt`**.
- `answer.txt` — **рядом с `task.json`**, не внутри `workspace`.
- Для coding проверяются изменённые исходники, поэтому правим файлы в
  `workspace`.
- В финальном наборе `expected` **убран**; харнесс его не читает.
- `task_type` и `reward` в `task.json` есть; баллы видны заранее.
- Финальный набор ограничен **4 типами** из примеров; сложность и структура
  похожи.
- Вопросы search-задач связаны со знаниями из `kb/`.
- Доступа в интернет нет, только API моделей.
- Можно использовать AgentForge-harness, но openJiuwen обязателен.
- Команда запуска контейнера будет опубликована 9 ноября — CLI делаем
  совместимым с опубликованным вариантом и с переменными окружения.

## 1. Цель и ограничения

Нужен Docker-образ, который запускается как

```bash
python /app/run_agent.py --tasks-dir /data/tasks
```

и за **1 час** и **100 000 выходных токенов** набирает максимум `reward` за
задачи, записывая `answer.txt` рядом с `task.json`.

| Ограничение | Значение |
| --- | --- |
| Время работы | 1 час (внешний `timeout`) |
| Бюджет | 100 000 выходных токенов; 10 входных = 1 выходной |
| Модели | 4 штуки через прокси, переключение на каждом вызове |
| Параллельность | до 5 сессий агента |
| Ресурсы | 4–8 CPU, 16 GB RAM, без GPU |
| Сеть | только прокси моделей; ничего не скачивать при запуске |
| Образ | < 4 GB, сборка < 1000 с |
| Репозиторий | < 100 MB без `.git` |

Баллы случайны и не связаны со сложностью; 15–25% задач невыполнимы. При
бюджете 100K выигрывает не «самый умный агент», а тот, кто **бесплатно**
решает типовые задачи и тратит LLM-токены только там, где без них нельзя.

## 2. Проверенные факты об openJiuwen

Проверено по wheel-пакетам с PyPI и пробной сборкой Docker:

- `openjiuwen==0.1.19` ставится на Python 3.11–3.13 (в образе будет 3.11).
- Публичный API:
  - `openjiuwen.core.foundation.llm.schema.config.ModelClientConfig` —
    `client_provider`, `api_key`, `api_base`, `timeout`, `max_retries`;
  - `ModelRequestConfig` — `model`, `temperature`, `top_p`, `max_tokens`;
  - `openjiuwen.core.foundation.llm.model.Model` — `await model.invoke(...)`,
    возвращает `AssistantMessage`;
  - `AssistantMessage.usage_metadata` содержит `input_tokens`,
    `output_tokens`, `reasoning_tokens`, `total_tokens`, `cache_tokens`.
- Именно в 0.1.19 появилось поле `reasoning_tokens`, поэтому версию фиксируем
  на `0.1.19`. В публичном PyPI версия есть; в некоторых внутренних зеркалах
  максимум — 0.1.13.post1, поэтому в Dockerfile явно указываем
  `--index-url https://pypi.org/simple`.
- В пакете есть `DeepAgent`/`create_deep_agent`, `ReActAgent`, тулы
  `BashTool`, `ReadFileTool`, `WriteFileTool`, `GrepTool`, `GlobTool`.
- Провайдер `OpenAI` в openJiuwen — это OpenAI-совместимый клиент, поэтому
  прокси подключается через `api_base` без хаков.
- Пробная сборка `python:3.11-slim-bookworm` + `pip install openjiuwen==0.1.19`
  дала образ **1.41 GB**; импорт `Model` работает. Запас до 4 GB большой.

## 3. Главная идея: гибридный каскад

Не «один универсальный ReAct-агент на каждую задачу», а каскад:

```
            ┌──────────────────────────────┐
            │  Загрузка 100 задач + reward │
            └──────────────┬───────────────┘
                           ▼
            ┌──────────────────────────────┐
            │  Бесплатная фаза (0 токенов) │
            │  триаж + детерминированные   │
            │  решатели + mutation repair  │
            └──────┬───────────────┬───────┘
                   │ решено        │ не решено
                   ▼               ▼
            answer.txt      ┌──────────────────┐
                            │  Выполнимость и  │
                            │  оценка стоимости│
                            └────────┬─────────┘
                                     ▼
                    ┌────────────────────────────────┐
                    │  Дешёвые LLM-обработчики       │
                    │  math / data / search / coding │
                    │  (noreason, малый max_tokens)  │
                    └──────────────┬─────────────────┘
                                   │ не вышло
                                   ▼
                    ┌────────────────────────────────┐
                    │  Компактный ReAct / DeepAgent  │
                    │  (только для сложного)         │
                    └────────────────────────────────┘
```

Почему так:

1. **Детерминированные решатели** для четырёх известных типов стоят
   0 токенов. При бюджете 100K это основной источник баллов.
2. **Mutation repair** для coding: тесты запускаются локально, а типовые баги
   (не тот оператор, `sorted` вместо `reversed`, `% 2 == 1` вместо `== 0`)
   исправляются перебором мутаций AST. Токены не тратятся.
3. **Один короткий LLM-вызов** вместо 5–10 шагов ReAct экономит входные
   токены: каждый шаг заново отправляет всю историю.
4. **Локальная проверка** (тесты, пересчёт, grep) не даёт записать неверный
   ответ.
5. **Универсальный loop** — только fallback для незнакомых вариаций.

## 5. Поток выполнения

```python
async def main(cfg):
    tasks = load_tasks(cfg.tasks_dir)       # рекурсивно, без __MACOSX
    meter = TokenMeter(cfg.budget)          # BUDGET из env
    llm = LLMRouter(cfg, meter)
    planner = Planner(tasks, meter, cfg)

    # Фаза 0: бесплатный триаж и детерминированные решения (0 токенов)
    await run_local_phase(tasks, workers=cfg.cpu_workers)

    # Фаза 1: LLM-задачи по убыванию reward/стоимость, 3 воркера по умолчанию (до 5)
    await run_llm_phase(planner.ordered(), workers=5)

    # Финал: сохранить solutions.json/summary; answer.txt только там,
    # где есть ответ (для impossible файл не создаём)
    flush_state()
```

Порядок фаз важен: пока идёт бесплатная фаза, бюджет не тратится. Если
прокси/бюджет откажет, ответы за простые задачи уже будут на диске.

## 6. Учёт токенов и бюджет

### 6.1. Формула

```
cost = output_tokens + input_tokens / 10
```

Считаем в целых десятых: `cost_x10 = output_tokens * 10 + input_tokens`.

- `input_tokens` — из `usage_metadata.input_tokens`, включая кешированные
  (по регламенту кеш не даёт скидки).
- `output_tokens` — из `usage_metadata.output_tokens`.
- Reasoning: если `reasoning_tokens > output_tokens`, провайдер вернул их
  отдельно и не включил в `completion_tokens`; тогда
  `output = output_tokens + reasoning_tokens`. Иначе `output_tokens` уже
  включает рассуждения.
- Если `usage` нет — оценка через `tiktoken` с коэффициентом 1.3 и пометкой
  `estimated=True`.
- Для проверки бюджета используем **консервативную** оценку:
  `effective_cost = cost * 1.10`.

### 6.2. Политика при BUDGET=100000

- `BUDGET` читается из env; при отсутствии — 100000 и предупреждение.
- Жёсткий стоп новых LLM-вызовов при `spent >= BUDGET * 0.95` (95 000).
- Резерв 5 000 на ретраи, неточность учёта и финальные вызовы.
- Перед каждым вызовом: `estimate(input) + max_tokens` сравнивается с
  остатком; если не влезает — понижаем модель/`max_tokens` или пропускаем.
- Прокси не сообщает остаток, поэтому при `402/403/quota` или серии
  таймаутов считаем бюджет исчерпанным, прекращаем новые вызовы и сохраняем
  всё, что есть.
- Бюджет тратим «волнами»: сначала бесплатные задачи, затем дешёвые
  LLM-задачи, затем дорогой coding/generic.

### 6.3. Лимиты на задачу

| Тип | Базовый cap, cost | Комментарий |
| --- | --- | --- |
| deterministic (math/data/search) | 0 | только CPU |
| math fallback | 700 | 1 короткий вызов |
| data fallback | 900 | 1 короткий вызов |
| search fallback | 700 | 1–2 коротких вызова |
| coding (после mutation repair) | 3 000 | 2–3 LLM-итерации |
| generic | 2 500 | 4–6 шагов |

`cap = base * (1 + reward / 5)`, но не больше остатка после резерва.
При превышении задача останавливается, сохраняется лучший проверенный ответ.

### 6.4. Ожидаемая раскладка 100K

Пример: 25 coding, 60 math/data/search, 15 прочих/невыполнимых.

| Статья | Оценка |
| --- | --- |
| бесплатная фаза (60 задач + часть coding) | 0 |
| coding LLM (25 × до 2 500) | ≤ 62 500 |
| fallback math/data/search (15 × 700) | ≤ 10 500 |
| триаж/судья | ≤ 2 000 |
| резерв/ретраи | 5 000 |
| **итого** | **≤ 80 000** |

Если mutation repair решает большую часть coding, фактический расход будет
ещё ниже. Это важно и для победы, и для tie-break по токенам.

## 7. Триаж: тип, выполнимость, стоимость

### 7.1. Тип

Берём `task_type` из `task.json` (организаторы подтвердили, что поле есть).
Дополнительно — эвристики по инструкции и файлам на случай новых значений.

### 7.2. Бесплатные сигналы выполнимости

- **data**: файл существует, нужные колонки есть, фильтр не пустой; если
  строк 0 или колонки нет → `impossible`.
- **search**: сущность из вопроса находится в `kb/`; если нет → `impossible`.
- **coding**: тесты запускаются; если падают с `SyntaxError` в тестах,
  `ImportError` на отсутствующий модуль, или тест содержит заведомо
  невыполнимое утверждение (`assert 1 == 2`) → `impossible`.
- **math**: все числа и операции извлекаются; если в условии есть
  противоречие/недостающее данное → `impossible`.
- `expected` в финале отсутствует и удалён из модели задачи. Локальный
  ground truth (если нужен) лежит в отдельном `_truth.json`, который харнесс
  не читает.

### 7.3. LLM-судья (только при неопределённости)

Один вызов `noreason`, `max_tokens=60`:

```
Decide if the task is solvable with the given files and tools.
Answer with JSON only: {"solvable": true|false, "confidence": 0..1,
"reason": "<=12 words"}.
Task: ...
Files: ...
```

Судья запускается только если локальные сигналы не дали ответа и
`reward >= 3`. При `confidence < 0.6` считаем задачу выполнимой: дешёвая
попытка лучше пропуска прибыльной задачи.

### 7.4. Оценка стоимости

До калибровки — таблица из 6.3. После прогонов на синтетике — `p80`
фактической стоимости по типу в `harness/calibration.json`. Онлайн —
скользящее среднее в рамках запуска.

## 8. Глобальный планировщик (портфель задач)

### 8.1. Почему per-task greedy недостаточен

Сортировка `reward / cost` — это эвристика для *дробного* рюкзака. У нас
0/1-рюкзак с неопределёнными стоимостью и успехом:

- две задачи с высоким `reward/cost` могут вместе не влезть в бюджет, а
  чуть менее выгодная третья — идеально добить остаток;
- у задач разная вероятность успеха `p_i`: дорогая coding-задача может
  стоить 3K и провалиться, а дешёвая search-задача — стоить 0 и решиться;
- бюджет общий, поэтому ценность задачи зависит от того, **что ещё есть в
  наборе**, а не только от её собственного отношения;
- 15–25% задач невыполнимы, и их нужно исключать до распределения бюджета.

Поэтому планировщик считает **глобальный вес** каждой задачи по всем 100
задачам сразу, а не решает каждую в отрыве.

### 8.2. Формальная модель

Для каждой нерешённой задачи после бесплатной фазы известно:

- `r_i` — `reward` из `task.json`;
- `p_i` — оценка вероятности решить задачу (0 для impossible);
- `c_i` — консервативная оценка стоимости (`p80`, не среднее);
- `t_i` — оценка времени.

Нужно выбрать подмножество `S`:

```
maximize   Σ_{i∈S} p_i * r_i
subject to Σ_{i∈S} c_i <= B_eff
           |S| <= available_workers * time_slots   (обычно не связывает)
```

где `B_eff = BUDGET - RESERVE` (95 000 из 100 000).

Это стохастический 0/1-рюкзак. Решаем его в два шага: теневая цена
(лагранжева релаксация) для динамического приоритета и DP для финального
портфеля.

### 8.3. Теневая цена бюджета λ — это и есть «общий вес»

Вводим λ — ценность одной единицы бюджета. Глобальный вес задачи:

```
w_i(λ) = p_i * r_i - λ * c_i
```

Задача выгодна, если `w_i(λ) > 0`: её ожидаемый вклад больше, чем стоимость
потреблённого бюджета. λ выбирается так, чтобы суммарная стоимость всех
выгодных задач примерно равнялась `B_eff`:

```
Σ_{i: w_i(λ)>0} c_i ≈ B_eff
```

Решаем бисекцией по λ (50 итераций, 100 задач — мгновенно). Это даёт
естественный коллективный вес: при жёстком бюджете λ растёт, и в портфель
попадают только задачи с лучшим соотношением `p_i*r_i / c_i`; при свободном
бюджете λ падает, и в портфель попадает больше задач.

Пример: coding с `p=0.6, r=5, c=2500` даёт `3.0 - 2500λ`; search с
`p=0.9, r=2, c=100` даёт `1.8 - 100λ`. При λ=0.001 coding имеет вес 0.5,
search — 1.7; search выгоднее. При λ=0.0005 coding — 1.75, search — 1.75;
задачи равны. Это и есть учёт всей совокупности, а не изолированный ratio.

### 8.4. DP по бюджету — финальный портфель

Теневая цена хорошо ранжирует, но не гарантирует, что набор влезет в бюджет
без «дыр» в конце. Поэтому после бесплатной фазы запускаем 0/1-рюкзак:

- дискретизация стоимости: 1 корзина = 100 cost-единиц;
- `dp[j]` — максимальный ожидаемый reward при стоимости ≤ `j`;
- 100 задач × 1000 корзин = 100 000 операций, доли секунды;
- восстанавливаем выбранное подмножество.

Если `p_i` и `c_i` неточны, DP даёт *план*, а не жёсткий контракт:
исполнение идёт по весам `w_i`, а после каждой задачи план пересчитывается.

### 8.5. Динамика и обучение на ходу

- После бесплатной фазы обновляем `p_i`, `c_i`, `r_i` и пересчитываем λ и DP.
- После каждой завершённой задачи обновляем статистику **по типу**:
  - `p_t` — Beta-постериор `(успехи + α) / (попытки + α + β)`;
  - `c_t` — `p80` фактических стоимостей (скользящее окно).
- Раз в 5 задач (или при отклонении факта от плана > 30%) пересчитываем
  портфель. Пересчёт дешёвый, поэтому можно хоть после каждой задачи.
- Новые задачи не добавляются — набор фиксирован, но оценки уточняются.
- Если фактическая стоимость оказалась ниже `p80`, освободившийся бюджет
  автоматически переходит задачам с наибольшим `w_i`; если выше — задачи с
  наименьшим весом отменяются до следующего LLM-вызова.

### 8.6. Учёт риска, времени и tie-break

- **Риск**: планируем по `c_i = p80`, а не по среднему; для задач с высокой
  дисперсией стоимости — штраф `β * σ_i`. Это не даёт одной дорогой задаче
  съесть бюджет.
- **Impossible**: `p_i = 0` → `w_i = -λ c_i < 0`, задача автоматически
  выпадает из портфеля. Для неопределённых задач `p_i` берём из триажа;
  сомнительные с высоким `reward` оставляем с `p_i = 0.5`, чтобы дешёвая
  попытка могла себя оправдать.
- **Время**: если осталось < 8 минут, в DP добавляется ограничение
  `t_i <= remaining`; дорогие задачи отбрасываются.
- **Tie-break**: при равном ожидаемом reward выбираем портфель с меньшей
  стоимостью. Формально максимизируем `Σ p_i r_i - ε Σ c_i` с малым `ε`;
  это помогает и в случае равенства баллов.
- **Резерв**: 5 000 cost-единиц не распределяем; он покрывает ретраи,
  недооценку reasoning и финальные вызовы.
- **Qualifier mode**: если задач ≤ 5, `B_eff` фактически равен всему
  бюджету, `p_i` завышаем, бюджетные пропуски отключаем — цена ошибки
  (вылет) выше экономии.

### 8.7. Псевдокод

```python
def build_portfolio(tasks, budget, reserve):
    live = [t for t in tasks if not t.done and not t.impossible]
    b_eff = budget - reserve

    # 1. Теневая цена
    lo, hi = 0.0, max((t.p * t.reward) / max(t.cost, 1) for t in live)
    for _ in range(50):
        mid = (lo + hi) / 2
        planned = sum(t.cost for t in live
                      if t.p * t.reward - mid * t.cost > 0)
        if planned > b_eff:
            lo = mid
        else:
            hi = mid
    lam = (lo + hi) / 2

    for t in live:
        t.weight = t.p * t.reward - lam * t.cost

    # 2. 0/1 DP по корзинам
    bucket = 100
    cap = b_eff // bucket
    dp = [0.0] * (cap + 1)
    take = [[False] * (cap + 1) for _ in live]  # для восстановления
    for idx, t in enumerate(live):
        cost = max(1, math.ceil(t.cost / bucket))
        value = t.p * t.reward
        for j in range(cap, cost - 1, -1):
            cand = dp[j - cost] + value
            if cand > dp[j]:
                dp[j] = cand
                take[idx][j] = True

    return recover_selected(live, take, cap), lam


async def run(tasks, budget):
    await free_phase(tasks)                 # 0 токенов
    selected, lam = build_portfolio(tasks, budget, reserve=5000)

    # 3 воркера по умолчанию (до 5); перед стартом задачи резервируем её cost
    async with WorkerPool(5, budget_guard=budget) as pool:
        for t in sorted(selected, key=lambda x: -x.weight):
            await pool.submit(t)

        # после каждой задачи/батча:
        # update_stats(t); selected, lam = build_portfolio(...)
```

### 8.8. Что это даёт по сравнению с простым ratio

- учитывает **весь набор**: λ и DP видят, что после выбора задач остаётся
  бюджет, и добивают его подходящими задачами;
- учитывает **вероятность успеха** и **риск стоимости**;
- автоматически исключает impossible (`p=0`);
- перераспределяет бюджет при отклонении факта от плана;
- при равных баллах выбирает более дешёвый портфель (tie-break);
- остаётся простым в реализации: ~100 строк на планировщик, без внешних
  библиотек.

## 9. Обработчики

### 9.1. math

1. **Шаблонный парсер (0 токенов).** Разбираем предложения по глаголам:
   `starts with N`, `ships X per day for D days`, `receives K deliveries of M`,
   `split equally into K ... rounded down`, `doubled`. Считаем на Python с
   `//`. Если разобраны все предложения — ответ без LLM.
2. **LLM → Python (1 вызов).** Просим только выражение:
   `Return ONLY a Python expression using the numbers from the task.`
   `max_tokens=100`, `temperature=0`. Выполняем в отдельном процессе с
   AST-whitelist (числа, `+ - * / // % **`, скобки).
3. **Fallback.** Один вызов reasoning-модели с просьбой вернуть только число.
   Не более 150 выходных токенов.

Проверка: целое число; диапазон правдоподобен.

### 9.2. data_analysis

1. **Детерминированный парсер (только точный шаблон).** Регуляркой
   распознаём ровно «How many units of product 'X' were sold in months A
   through B»; считаем через `csv.DictReader`, без pandas. Любая другая
   агрегация, фильтр или формулировка уходит в LLM: угадывать её нельзя.
2. **LLM → скрипт.** Короткий Python-скрипт, читает CSV, печатает одно число.
   Запускаем, берём последнюю непустую строку.
3. **Fallback.** Модель отвечает числом.

Проверка: число. Если файла/колонки нет, решение уходит в LLM fallback;
невыполнимой считается только отсутствующая таблица/данные.

### 9.3. search

1. **Локальный KB-граф (0 токенов).** Парсим markdown в
   `{entity: {field: value}}`. Поддерживаем:
   - «In which year was <person> born?» → `Born`;
   - «In which city is the headquarters of <person>'s employer?» →
     `Employer` → `Headquarters` (город до запятой);
   - «Who is the mentor of <person>?» → `Mentor`;
   - «Which company employs <person>?» → `Employer`;
   - «What industry is <company> in?» → `Industry`;
   - «When was <company> founded?» → `Founded`.
   Нормализация имён: регистр, пробелы, `_`/`-`.
2. **grep + LLM-извлечение.** Если шаблон не подошёл: grep по ключевым
   словам, 1–3 файла (до 6 KB), `noreason`, `max_tokens=50`.
3. **Impossible / fallback.** Если известный шаблон найден, а нужного поля
   в KB нет → impossible, `answer.txt` не создаём. Если сущность не найдена
   или шаблон незнаком → строгий LLM fallback; ответ принимается только если
   он стоит в одной строке с ключевым словом вопроса, иначе файл не создаём.

Проверка: ответ непустой, встречается в KB (нормализованно), без лишних слов.

### 9.4. coding

Самый дорогой тип, поэтому сначала **бесплатный mutation repair**:

1. Запускаем `python3 test_mylib.py` (или `python3 -m unittest discover -v`)
   в `workspace/`. Это бесплатно и даёт число падений.
2. Если тесты уже проходят → сразу `DONE`.
3. **Mutation repair (0 токенов).**
   - Берём только исходники (`*.py`, кроме `test_*.py`/`*_test.py`).
   - Генерируем мутации AST:
     - `+` ↔ `-`, `*` ↔ `/`;
     - `<` ↔ `>`, `<=` ↔ `>=`, `==` ↔ `!=`;
     - `+=` ↔ `-=`, `*=` ↔ `/=`;
     - `sorted` ↔ `reversed`;
     - `% 2 == 0` ↔ `% 2 == 1`;
     - `[:n]` ↔ `[-n:]`.
   - Сначала проверяем одиночные мутации, затем пары (beam search по числу
     упавших тестов). Для примеров достаточно пары мутаций.
   - Если тесты прошли — пишем `DONE`, токены не тратим.
4. **LLM patch-loop.** Если repair не справился:
   - минимальный промпт: инструкция, `mylib.py` (до 8 KB), тесты (до 8 KB),
     traceback (до 2 KB);
   - просим полное содержимое файла в формате
     `<<<FILE: mylib.py>>> ... <<<END>>>`, `max_tokens=500`;
   - 3 итерации `noreason`, затем 2 итерации reasoning-модели;
   - после каждой итерации запускаем тесты.
5. Тесты прошли → `answer.txt = DONE` рядом с `task.json`. Не прошли →
   `answer.txt` не создаём (неверный ответ не засчитается).

Токен-контроль: только релевантные файлы, обрезка, `temperature=0`.

### 9.5. generic

Fallback для незнакомых типов. По умолчанию **отключён**: свободный ответ
без проверки слишком легко ошибается на невиданных данных. Включается
`IRUNNER_ENABLE_GENERIC=1` для экспериментов:

- компактный ReAct на `openjiuwen.core.foundation.llm.Model`;
- инструменты: `bash`, `read`, `write`, `finish`;
- системный промпт ~200 токенов, максимум 5 шагов, `max_tokens=350`;
- native tool calling, при отсутствии `tool_calls` — текстовый JSON-протокол;
- `bash`: `cwd=workspace`, timeout 20 s, вывод до 8 KB;
- эскалация на reasoning-модель после 3 шагов без прогресса;
- опционально `--engine=deepagent`: `create_deep_agent` с `BashTool` и
  файловыми тулами для самых сложных случаев.

## 10. Модели и роутинг

| Ситуация | Модель |
| --- | --- |
| извлечение, классификация, короткие ответы | `qwen3.6-35b-a3b-noreason` |
| math/data скрипт | `qwen3.6-35b-a3b-noreason` |
| coding, первые итерации | `qwen3.8-27b-noreason` |
| coding, после 2 неудач | `qwen3.8-27b` |
| generic, первый шаг | `qwen3.8-27b-noreason` |
| generic, эскалация | `qwen3.8-27b` |

Параметры: `temperature=0`, `top_p=0.1`, `max_tokens` из обработчика.
Reasoning-модели — только при остатке бюджета и высоком reward, `max_tokens`
600–800, чтобы рассуждения не съели лимит. Переопределение через env
`MODEL_FAST`, `MODEL_SMART`, `MODEL_FAST_REASON`, `MODEL_SMART_REASON`.

`LLMRouter.call()` делает pre-check стоимости, ретраи (3 попытки, backoff на
429/5xx/timeout) и при 402/quota бросает `BudgetExhausted` без ретраев.

## 11. Конкурентность, время, отказоустойчивость

- `asyncio.Semaphore(5)` на LLM-задачи; локальная фаза — по числу CPU.
- Глобальный дедлайн: `start + 55 min` (запас 5 минут на flush).
- Пер-задачные таймауты: deterministic 30 s, math/data/search 60 s,
  coding 180 s, generic 180 s.
- `SIGTERM` (внешний `timeout`) → немедленный flush и выход.
- Прокси-ошибки: retry с jitter; после 3 неудач задача failed.
- `BudgetExhausted`: отменяем ожидающие LLM-задачи, дожидаемся текущих,
  сохраняем состояние, выходим с кодом 0.
- Логи: `logs/run.log`, `logs/traces.jsonl`; ключи и полные промпты не
  попадают в stdout.

## 12. Сохранение результатов

- `answer.txt` — **только рядом с `task.json`**, атомарно:
  `answer.txt.tmp` → `os.replace` → `fsync` каталога.
- **Для impossible и для задач без проверенного ответа файл не создаём.**
- Для coding правим исходники в `workspace/`, а `answer.txt` кладём рядом с
  `task.json` (организаторы подтвердили).
- После каждой задачи — строка в `solutions.jsonl`:
  ```json
  {"task_id": "...", "answer": "...", "solved": true, "reward": 3,
   "cost": 421.5, "method": "data_regex", "ts": "..."}
  ```
- `solutions.json` — атомарный снапшот всего состояния.
- `OUT` может быть каталогом или файлом:
  - каталог — `OUT/solutions.jsonl`, `OUT/solutions.json`, `OUT/summary.json`;
  - файл — JSONL туда;
  - не задан — `/tmp/irunner/...` (answer.txt всё равно в задачах).
- `summary.json`: сумма баллов, потраченный бюджет, разбивка по типам,
  список пропущенных с причинами.

## 15. Риски и открытые вопросы

| Риск | Митигация |
| --- | --- |
| 100K не хватит на все задачи | бесплатная фаза, mutation repair, жёсткие cap, приоритет reward/cost |
| Прокси не поддерживает native tools | текстовый JSON-протокол, авто-детект |
| Модель возвращает reasoning отдельно | эвристика `reasoning_tokens > output_tokens` |
| Impossible-детектор ошибается | пропуск только при явных сигналах; дешёвая попытка при высоком reward |
| `answer.txt` попал в impossible | отдельный флаг `impossible`; файл не создаём/удаляем stale |
| Таймаут 1 ч | soft deadline 55 мин, пер-задачные таймауты, flush после каждой задачи |
| Read-only root | пишем только в TASKS, /tmp, OUT |
| Ключи в репозитории | только env, `.dockerignore`, проверка `git grep` |
| Команда запуска изменится 9 ноября | CLI принимает и args, и env `TASKS`/`OUT`/`BUDGET` |

Осталось уточнить только организационные мелочи (точный формат `OUT`,
команда запуска). Архитектурных вопросов больше нет.
